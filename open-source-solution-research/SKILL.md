# 开源方案调研与选型

帮助个人开发者在 AI 辅助开发前找到适合当前需求的参考项目，并给出可核查的取舍。默认用中文；先看项目要解决的问题，再决定搜什么。

## 明确调研范围

- 从用户描述、已确认的需求或现有代码中提取所需能力、约束、当前技术栈和预期部署环境。用户给出的项目名称或链接是候选线索；先核实身份，不凭名称猜仓库。
- 明确这次是借鉴设计思路、复用部分代码，还是考虑引入依赖。三者的许可证、维护和改造要求不同。
- 用户指定候选数量或比较维度时遵从；未指定时先广泛发现，再选少量最相关的项目深入核查。没有合适候选时说明原因，不为凑数推荐。

## 搜索与核查

1. 用需求中的能力和同义术语搜索 GitHub；结合 README、文档、代码结构、发布记录、提交与 Issue 核对候选，不只看搜索摘要或 Star 排名。可先查看项目自身推荐的相关项目，再验证其来源。
2. 对入围项目统一记录：仓库链接与核查日期、热度、近期活跃度、许可证、主要技术栈、运行或部署门槛。热度可参考 Star 和使用者情况；活跃度需看近期维护与未解决问题；许可证需核对仓库原文及限制，缺失或不清楚就标为待核实。
3. 按与当前需求的贴合度筛选，不把大型框架的全部能力算作本项目所需。许可证、版本、活跃度和依赖条件会变化，报告中注明观察时点与证据范围。
4. 对每个入围项目指出可直接借鉴的文档、流程或模块，需要二次定制的部分，粗略改造成本及其依据，并列出主要风险。区分“参考思路”和“复制代码”；未经核查不承诺可直接集成。

## 输出与决策

- 完整调研结束后交付调研报告，不只在聊天中给结论。默认保存为项目中的 Markdown 文件：沿用已有调研目录或使用 `docs/research/<主题>.md`，报告完成后提供文件链接。写入前检查已有内容，避免覆盖无关记录；项目位置不明确时先展示报告并询问保存位置，不擅自选项目。用户指定只在对话中交付时遵从。
- 先给一张紧凑比较表，再逐项解释适用场景、复用边界、成本和风险；附可打开的仓库链接及支撑关键判断的 README、许可证或发布记录链接。无法核实的维度明确写“未核实”，不编造数字。
- 给出推荐顺序及原因，并说明与项目当前阶段的关系：现在采用、先做小实验，或暂缓。推荐是供用户判断的建议，不自动变成已确认的技术方案。
- 用户决定采用某候选后，形成简短交接：选定范围、要验证的假设、许可注意点、最小试验和成功标准。需要分配版本时交给路线图环节；本 Skill 不自行下载、复制代码、改仓库或安装依赖，除非用户另行明确要求。

## 调研报告内容

按调研复杂度组织，至少保留以下可追溯信息：

- **目标与范围：** 要支持的项目决策、调查方向、约束和未覆盖范围。
- **主要发现与结论：** 比较结果、推荐及理由、对当前项目的影响。为关键判断关联具体来源，区分已查阅事实、推断和待验证假设；搜索摘要或未实际查阅的资料不能冒充核查证据。
- **资料与来源：** 记录资料名称、原始链接、查阅日期、简短内容摘要及其支持的发现。可用来源编号关联正文；代码或版本敏感结论尽量指向具体文件、版本或提交，而不只列仓库首页。
- **参考价值：** 说明各资料值得借鉴的思路、流程或模块，以及适合本项目的哪个部分。
- **可二次复用内容：** 明确代码、组件、设计、数据、工具或方法的具体位置、用途和复用方式，区分参考思路、候选复用和已核实可复用。没有合适复用内容时如实写明。
- **复用条件与成本：** 附许可证或授权依据，说明署名及分发要求、技术依赖、适配工作、粗略成本及使用限制。公开可访问不等于允许复制；授权不明时标为待核实，不承诺可直接复用。
- **建议与未决问题：** 下一步验证、成功标准、风险和待用户决定的事项。未运行或未集成的候选明确标注，不能把文档核查等同于实际验证。

后续 PRD、设计和路线图交接引用报告位置及相关结论；报告中的建议只有经用户确认后才能作为已确认决策。链接可能失效，摘要应保留足够上下文，避免后续必须重读全部资料才能理解结论。

## 边界

- 开源项目是参考资料，不能代替对当前仓库和实际运行的检查。
- 不以“Star 高”替代需求匹配或维护质量，也不把近期一次提交等同于项目持续健康。
- 临时查一个事实或快速找链接时可直接给简短答案与来源，无需建立完整报告；涉及完整比较或选型时应交付报告，直接复用代码或长期依赖时更仔细核对许可证、维护状态和部署条件。
