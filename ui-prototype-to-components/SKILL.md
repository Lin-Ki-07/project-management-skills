# UI 原型与组件交接

把已确认的用户场景转成能看、能讨论、能逐步实现的界面方案。默认用中文；尊重用户指定的设计工具、模型和现有设计系统。

## 确定设计输入

- 先读当前需求、已有页面或设计材料，找出目标用户、关键任务、内容、约束和验收要点。现有项目还应检查相关页面与样式，避免原型脱离实际数据和交互。
- 明确本轮要设计的页面或流程，以及需要展示的设备尺寸。未确认的产品规则标为待定，不在视觉稿中悄悄定案。
- 默认先用 Image 生成效果图，视觉方向确认后直接用 Figma 制作原型，不生成 HTML 原型；用户明确指定其他形式时遵从用户选择。实际执行时加载对应的 imagegen 或 Figma 技能，按其说明调用工具。
- 所需工具不可用时，说明受影响的步骤并与用户商量替代方案，不自动退回 HTML。

## 按需搜集视觉参考

- 用户对 UI 风格想法模糊，且没有提供参考图片、网站或可沿用的设计规范时，先上网搜集 5 个相关设计案例，再生成效果图。已有清楚的视觉要求或参考资料时跳过此步骤。
- 优先选同类产品或相近任务的界面；5 个案例在布局、配色、信息密度或风格上应有明显差异，帮助用户比较方向。
- 尽量展示可查看的截图或预览，并附真实来源链接。每个案例简要说明值得参考的设计及其与当前场景的关系。无法展示图片或无法找到足够案例时如实说明，不虚构案例或来源。
- 让用户选择一个方向或组合不同案例的偏好，将选择整理为视觉要求后继续。借鉴设计思路，不直接照搬案例的品牌、内容和整套界面。

## 生成效果图并确认视觉方向

1. 根据需求和已有参考，用 Image 生成关键页面的正面界面效果图，展示主要布局、配色、信息层级和真实感足够的内容，避免设备外壳、场景背景等干扰界面评审的装饰。
2. 优先用一个有代表性的页面确定视觉方向，再按需要扩展其他页面。让用户评审整体风格、布局和信息层级，记录已确认决定与待修改点；方向未定时先修改效果图，不直接进入 Figma 制作或整页代码实现。
3. 效果图用于确认视觉方向，不证明交互可用或功能已实现；生成图片中的文字和细节问题应在后续 Figma 设计中纠正。

## 制作 Figma 原型并评审

1. 依据已确认的效果图和视觉要求，在 Figma 中制作可编辑的页面结构，落实文字、间距、组件和关键状态，不将整张效果图贴入 Figma 冒充完成原型。
2. 根据实际流程呈现弹窗、加载、空状态、错误、选中和窄屏等关键状态。按需要及工具能力连接跳转和交互，明确哪些已经连接、哪些仅为状态展示；静态页面不冒充已验证的交互。
3. 提供可访问的 Figma 链接和必要的预览，让用户评审页面内容组织、操作路径和状态变化。记录确认结果与修改点，原型未确认时先修改设计，不直接转成整页代码。
4. 避免不必要的辅助标签与说明，让布局本身发挥解释作用。优先用分组、按钮名称、图标和状态表达功能；检查页面是否出现每个按钮后都跟着一段解释的情况。错误、风险、不可逆操作及无障碍所需文字仍应清楚。

## 拆分组件并交接

- 原型方向确认后，列出页面区域、可复用组件、各组件的输入与状态、交互事件、数据来源和异常状态。按职责与复用价值拆分，避免把每个装饰元素都做成独立组件。
- 给出适合逐项开发的顺序和每项可观察的验收结果；标清哪些组件沿用现有实现，哪些需要新增或局部修改。需要接口或真实数据时列出依赖，不把视觉占位内容当作已接通功能。
- 将确认的原型、状态说明、组件清单和未决问题交给前端实现环节。开发时按组件核对视觉与行为；如实现发现约束冲突，回到设计决定更新交接，而不是悄悄偏离原型。

## 边界

- 产品目标与业务规则由需求发现环节确认；本 Skill 负责把它们表达成界面方案，不自动新增功能。
- 原型、效果图或组件清单不证明代码已实现；浏览器中的视觉、交互和无障碍结果须在实现后另行验证。
- 新页面或较大改版默认遵循效果图确认后再制作 Figma 原型的流程。已有页面只涉及按钮、间距或局部状态等小改动时，可直接调整 Figma 或用局部示意和明确的前后状态完成评审，不要求重新生成整页效果图。
