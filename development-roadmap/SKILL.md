# 开发路线图与版本计划

帮助个人开发者把已确认的产品目标转成可推进、可核查、可跨对话接续的开发计划。默认用中文；沿用项目已有的版本和编号习惯。

## 先确定真实基线

- 新项目或新增功能先读取覆盖本轮范围且经用户确认的 PRD，并记录文档位置或对话版本及确认依据；一般需求记录不能替代 PRD。现有项目还应检查适用的项目说明、路线图、版本记录、相关代码和 Git 状态。只读取制定当前计划所需的材料。
- 分开标记“已确认需求”“建议”“假设”“暂缓项”。路线图、提交说明和口头报告不能单独证明功能已实现；完成状态应以代码和适当的运行或验收证据为准。
- 输入不足时，可按已知内容给出可讨论的计划草案；仅询问会改变范围、顺序或验收边界的关键问题。新项目或新增功能缺少已确认 PRD 时，明确草案不能作为开工依据，先交回需求收敛与 PRD 确认，不交给正式页面设计或功能实施。
- 已有项目的小修复、文案或间距调整，可依据明确的目标与验收要求安排，无需补完整 PRD。影响范围、核心流程或业务规则的变化，先更新相关 PRD 并由用户确认，再安排受影响工作的实施；已有确认记录时不重复询问。

## 组织计划

- 依据用户目标区分北极星 Demo、后续迭代与面向实际使用的版本。Demo 可直接接收已确认的轻量 PRD（含可引用的对话版本），不要求扩写完整产品 PRD 或补齐远期规划。
- 北极星 Demo 围绕一条核心价值链路安排少量近期步骤，优先打通从输入到结果的完整流程；账号、后台、同步等外围能力仅在当前链路确实依赖时纳入。远期方向记为暂缓或建议，不拆完整任务、不承诺工期。
- 写清哪些能力真实打通、哪些外围部分允许模拟，以及各自能证明什么。核心价值依赖的能力不得用固定结果代替后标为验证通过；技术可行性或调用条件有关键缺口时，只安排最小核实步骤，不扩成全面调研。
- 设计步骤只覆盖当前链路的页面和关键状态：效果图用于视觉定稿与 Figma 参考，Figma 原型用于界面开发，业务规则依据 PRD。首次设计按效果图定稿 → Figma → 实现安排；局部迭代沿用已确认方向，只更新受影响内容。HTML 仅在 Figma 无法调用且恢复尝试无效后作为兜底方案讨论。
- 简单 Demo 可用一张步骤表加当前／下一步，不强制划多阶段、另建交接文件或重复抄写 PRD 与工作日志。已有确认与实施授权继续沿用，只对影响方向的新决定请求确认。

项目没有路线图格式时，可将 [路线图模板](assets/ROADMAP.md) 复制到项目的 `docs/ROADMAP.md` 并填写；已有文件时沿用现有格式。模板字段可按项目规模删减，验收、状态、依赖和证据入口仍需清楚。需要处理需求变更、步骤替代或与工作日志衔接时，按需阅读 [需求变更案例](references/change-example.md)；案例为虚构试填，不作为真实完成证据。

1. 写清目标与验收边界，说明本轮覆盖哪个项目或版本，以及明确排除的内容。
2. 按依赖关系划分阶段，再把近期阶段拆成一次可推进、可验证的小目标。每项给出编号、具体产物或行为、可观察的验收结果和状态；远期目标可以较粗，但标出待细化的决定。
3. 区分已完成、待验证、当前、待开始、暂缓和可选。代码已写但未跑过所需验证时标为“待验证”；原方案被替代时保留变更缘由与去向，不悄悄改写历史。
4. 对每个阶段说明交接条件：哪些结果必须检查，哪些限制必须记录。先核对仓库已有的分支和版本惯例，再按并行工作、改动风险及独立评审需要建议是否另开分支；小而连续的修复可沿用当前工作分支。需要新分支时写明起点、用途和合并前验收条件，不自动创建分支、提交、推送、合并、打标签或发布。
5. 展示本轮已确认范围的编号小目标、验收结果及必要阶段，指出当前一步和下一步；远期内容仅列方向。按用户已有选择与授权交给实施或设计环节，不为计划流转重复审批；本 Skill 不代替详细技术设计。

交给代码实施时，附上当前阶段和步骤编号、验收结果、分支建议及工作日志位置。提醒实施者正式写代码前向用户报告 Git 状态和分支建议，并给出简要实施与验证计划；已有授权的工作不增加重复审批。新分支沿用项目约定，无约定时建议 `codex/<主题>`，具体基线须先核实。

## 维护与交接

- 有调研报告时引用报告位置及与当前目标有关的结论、复用条件和待验证事项，把适配工作与许可等依赖带入计划；未确认的调研建议仍标为建议，不自动安排为已确定方案。无需为引用报告复制整份内容，也不要求无调研的工作补报告。
- 需求变化、发现新问题或验证失败时，说明受影响的目标、依赖和版本；小修复可插入当前阶段，范围明显扩大的工作建议独立阶段，并由用户决定。
- 更新已有路线图时，先读原文，说明是追加还是局部替换，检查修改内容，保留未受影响的记录。仅在证据满足验收条件后勾选完成。
- 每个代码实施小步骤完成、失败或受阻时，要求及时记录实际改动和验证到项目工作日志，默认 `docs/WORKLOG.md`，已有日志则沿用。阶段结束时追加小结；路线图保留当前计划和状态，工作日志保留历史过程，交接摘要引用二者的位置。没有实际实施时不虚构日志。
- 每次交接留下一段简短摘要：当前分支与工作区状态、已验证结果、未验证或暂缓事项、下一小目标及其验收方式。阶段结束、长阶段中途换会话或跨 AI 接续时，可按仓库的 `templates/HANDOFF.md` 在具体项目中建立或更新交接文档；不要求每个小改动都写完整文档。
- 交接文档只保留接手所需的当前事实和入口。更新已有文件前先读原文，替换过期状态并检查 diff；开发历史过程留在工作日志，版本发布变化留在版本记录。接手者仍需重新核对 Git、相关代码和必要的运行结果。
- 单独安装本 Skill、无法取得上述模板时，沿用项目已有交接格式，至少记录目标与当前一步、仓库核对入口、已完成及验证证据、阻碍和已知问题、无效尝试及原因、下一步与验收、协作约定。仅在使用者的项目中填写实际状态。

## 边界

- PRD 中的用户场景和业务规则由需求发现环节负责；这里把已确认的要求安排为开发步骤，不自行升级未确认的建议。
- 技术选型、UI 原型、代码实现、测试执行和 Release 发布各有独立工作；本 Skill 只规定它们在路线图中的目标与验收接口。
- 根据实际项目决定流程深度。个人小项目可以只维护一份 Markdown 路线图；无需模拟多人审批或为每个小改动建立完整文档包。
