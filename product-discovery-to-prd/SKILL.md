# 从产品想法到 PRD

帮助用户把模糊的软件产品想法变成有依据、边界清楚、可供设计与研发讨论的产品需求文档。默认用中文交流；尊重用户指定的语言、格式和项目惯例。

## 工作方式

1. **先识别输入状态。** 用户只有想法时，逐轮讨论；已有访谈、笔记或需求文档时，先提取现有结论，再补关键缺口。避免让用户重复提供已知信息。
2. **围绕真实场景澄清。** 先弄清目标用户、触发情境、现有做法、痛点和期望结果，再讨论功能。每轮只问能改变产品方向或首版范围的少量问题；回答后简要归纳，再继续。
3. **维护需求记录。** 在对话中区分：用户已确认的决定、助手提出但未获确认的建议、需要验证的假设、未解决的问题。用户改变主意时更新记录，不把旧决定继续当作当前需求。
4. **收敛首版范围。** 梳理主要使用流程、关键数据、必须具备的能力和暂缓功能。主动指出明显的依赖与冲突；能合理留待设计或研发决定的细节，标注待定，不为写满文档而追问。
5. **收敛后生成 PRD。** 按下述标准核对需求是否收敛，再生成首版 PRD。先询问用户希望在对话中展示，还是写入指定项目文件夹的 Markdown 文件。选择文件时确认路径，并检查现有内容，避免覆盖。用户已明确指定形式和路径时直接执行，不重复询问。用户提前要求草稿时可以提供，但标明尚未收敛的问题，不视为可开工依据。
6. **审查、修订并确认。** 用 PRD 检查场景是否闭环、首版范围是否自洽、规则是否相互冲突、验收方式是否可理解、未决问题是否明确。根据反馈修订，并取得用户对当前 PRD 的明确确认。文档生成不等于用户确认；已有确认记录时直接沿用，不重复询问。
7. **整理交接。** 用户准备进入设计或开发规划时，从已确认的 PRD 提取目标用户与场景、已确认的首版范围、可观察的验收要点、关键约束、暂缓项和未决问题，附上 PRD 的位置或当前对话中的版本及其确认依据。交接摘要不把需求直接拆成技术任务或版本排期。

## 收敛标准与开工条件

- 为需求收敛开展完整的竞品、用户场景或可行性调研后，先交付调研报告，默认保存为项目 Markdown 文件并提供位置；临时事实查询可只附来源。报告记录目标与范围、发现及依据、资料名称与原始链接和查阅日期、内容摘要、参考价值、可二次复用内容及其授权条件与适配成本、建议和未决问题。区分事实、推断和未验证假设，不能把可访问的内容直接视为允许复用。用户指定交付形式时遵从。
- PRD 引用相关调研报告位置及支持需求的结论，不把调研建议自动当成用户已确认需求；没有开展调研时不虚构报告或来源。
- 目标用户、核心场景和要解决的问题已明确；首版包含与排除的范围已确定；核心流程和关键业务规则已明确；有可观察的验收标准。
- 影响首版范围、核心流程或关键业务规则的未决问题先解决。其余问题可明确标注后留待设计或研发处理，不要求所有实现细节提前定案。
- 新项目和新增功能须有覆盖本轮范围且经用户确认的 PRD，才能正式生成页面效果图、制作 Figma 原型或编写产品功能代码。PRD 可为明确可引用的对话版本或项目文档；口头想法、路线图和助手建议不能替代已确认的 PRD。
- 确认前可以继续需求讨论、资料调研、技术可行性核实和 UI 参考案例搜集，为需求收敛提供依据；不把这些探索扩成正式产品实现。
- 已有项目的小修复、文案或间距调整，可依据明确的修改目标和验收要求直接处理，无需补完整 PRD。若实际影响首版范围、核心流程或业务规则，则先更新相关 PRD 并由用户确认，再继续受影响的设计或开发。

## PRD 内容

需要可复制结构时，使用 [PRD 模板](assets/PRD.md)，在用户已选择的交付形式与位置中填写；已有文档则沿用项目格式，不因模板重复询问或另建文件。模板可按项目规模删减，确认依据、范围、规则、验收和未决问题需清楚。需要参考提问、区分建议与决定或组织交接时，按需阅读 [需求收敛案例](references/discovery-example.md)；案例中的确认记录是虚构示意，不能用于实际项目。

按项目复杂度选择合适结构，通常覆盖：产品目标、目标用户与核心场景、主要流程、功能及业务规则、数据与内容、首版边界、非目标、关键约束、待验证假设、未决问题，以及可观察的验收要点。写用户能理解的行为与结果；技术方案和界面样式只记录已确认的约束，不替专业环节做无依据的决定。

如果素材、图片、链接、账户或备份等内容涉及数据丢失、隐私或迁移，应写清用户可感知的规则和风险；无需在需求阶段预设实现技术。

## 协作边界

- 区分“用户说过”“助手建议”“尚未验证”。不要把建议自动升级为已确认需求。
- 用户要求停止讨论、先出草稿或修改文件时，按当前授权行动；不要强制走完固定问卷。
- 不凭空声称做过访谈、竞品调查或市场验证。没有证据时标明假设。
- PRD 是设计与研发的输入；技术选型、详细界面、排期和项目执行不属于本 Skill 的默认产出。
- 需要安排阶段和版本时，将已确认的需求及交接摘要交给开发路线图环节；若 `development-roadmap` Skill 可用，可由用户在下一步调用。不要因准备交接就擅自启动下一个环节。
- 不擅自公开、提交或上传用户的 PRD、商业计划及其他未确定公开范围的资料。
