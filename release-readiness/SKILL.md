# 测试与版本收尾

帮助个人开发者判断一个阶段或版本是否达到事先约定的验收边界，并把结果写成可复查的交接材料。默认用中文；沿用项目已有版本规则。

## 核对收尾范围

- 先读取当前版本目标、适用项目说明、近期变更和 Git 状态。计划、提交信息与口头报告只是线索；实际完成情况以代码和可复查的验证结果为准。
- 列出本版必须验收的小目标、已明确顺延的工作和已知限制。原方案被用户取消或替代时，写明去向，不把它作为仍需通过的旧验收项。
- 根据影响选择回归范围：运行相关自动检查，必要时核对真实界面、数据读回或外部集成。实际未运行的检查写“未验证”，不要用模拟、构建或截图替代更强的证据。

## 形成验收结论

1. 对每项给出预期、实际、证据及状态：通过、失败、待验证或顺延。失败或关键证据缺失时，指出阻碍收尾的具体条件和最小补验步骤。
2. 检查本版改动是否引入明显回归，并核对工作区中的未提交文件。保留用户自己的改动；不要把工作区干净、远程同步或标签存在当作未经检查的事实。
3. 只有必需目标满足验收边界时，才表述为“版本计划内工作完成”。这不代表质量已全面证明；注明样本范围、未覆盖场景和后续阶段任务。

## 更新材料与交接

- 按实际结果更新 README、路线图和版本记录。修改已有文件时，说明追加、局部替换或完整替换，检查 diff，避免覆盖其他内容；不要求把所有内部工作笔记公开发布。
- 提供与当前代码一致的 Release 标题和说明草稿，包括主要变化、验证与限制。发布前再次核对目标分支或提交；若代码或文档随后变化，更新草稿中受影响的结论。
- 给出下一阶段交接摘要：当前分支与工作区、已验证能力、未验证和顺延项、下一步目标及验收方式。必要时提供可粘贴到新对话的提示词，但提醒接手者重新核查仓库状态。
- 提交、推送、合并、打标签和发布按用户授权与仓库约定进行；整理草稿不等于执行这些操作。

## 边界

- 单个功能的开发和局部验证由实施环节负责；本 Skill 汇总版本级证据并补足必要的回归。
- 测试深度按风险决定。低影响变更不因“版本收尾”而强制生成大量重复测试；持久化、删除和不可逆操作需要与其风险相称的验证。
