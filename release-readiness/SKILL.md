# 测试与版本收尾

帮助个人开发者判断一个阶段或版本是否达到事先约定的验收边界，并把结果写成可复查的交接材料。默认用中文；沿用项目已有版本规则。

## 核对收尾范围

- 先按用户目标区分北极星 Demo、后续迭代与面向实际使用的版本。Demo 直接引用已确认的轻量 PRD 与当前路线图，只验收约定的核心链路，不为收尾补齐账号、后台、同步或正式发布能力；不得临时降低已确认的必需验收条件。
- Demo 核心验收覆盖从真实输入到结果的应用流程及影响演示的关键失败处理。模型、检索等核心价值依赖的能力须有真实调用证据；外围模拟按已确认边界注明，不能用离线模拟、固定答案或请求成功单独证明核心价值成立。
- 涉及界面时按已确认的 Figma 页面或节点核对当前链路与关键状态，业务规则依据 PRD，效果图不作为实现验收依据。若采用已同意的 Figma 不可用兜底方案，注明临时依据及限制，不虚称完成 Figma 验收。

- 先读取当前版本目标、适用项目说明、近期变更和 Git 状态。计划、提交信息与口头报告只是线索；实际完成情况以代码和可复查的验证结果为准。
- 列出本版必须验收的小目标、已明确顺延的工作和已知限制。原方案被用户取消或替代时，写明去向，不把它作为仍需通过的旧验收项。
- 根据影响选择回归范围：运行相关自动检查，必要时核对真实界面、数据读回或外部集成。实际未运行的检查写“未验证”，不要用模拟、构建或截图替代更强的证据。

## 形成验收结论

需要组织验收材料时，可使用 [验收与收尾模板](assets/ACCEPTANCE.md)，按用户选择的交付形式填写；已有记录则沿用格式，不重复建档。需要判断证据缺口、顺延事项或草稿状态时，按需阅读 [版本收尾案例](references/closeout-example.md)。案例为虚构试填，不作为真实验收或发布证据。

1. 对每项给出预期、实际、证据及状态：通过、失败、待验证或顺延。失败或关键证据缺失时，指出阻碍收尾的具体条件和最小补验步骤。
2. 检查本版改动是否引入明显回归，核对当前分支与工作区中的未提交文件；涉及合并或发布时再核对目标分支和尚未合并的相关改动。说明验收所依据的提交或工作区状态；有发布安排且与计划来源不一致时，标明差异及补验条件。保留用户自己的改动；不要把工作区干净、远程同步或标签存在当作未经检查的事实。
3. 只有必需目标满足验收边界时，才表述为“版本计划内工作完成”。这不代表质量已全面证明；注明样本范围、未覆盖场景和后续阶段任务。

Demo 必需条件满足时使用“约定的 Demo 演示验收通过”，明确真实能力、外围模拟与未覆盖范围，不等同于可正式使用或已发布。用户尚未试用、试读时，核心价值反馈标为待收集；若该反馈是约定的必需验收，缺失时不能判定通过。反馈不佳时据事实调整下一轮，不把“程序能运行”写成“产品价值已验证”。

## 更新材料与交接

- 用户要求新写、整理或改进项目 README 时，可单独执行文档任务，不要求先跑完整验收流程。先按 [README 编写规范](references/readme-guide.md) 核实项目事实，再按需使用 [项目 README 模板](assets/PROJECT-README.md)；已有格式和明确用户选择优先，Demo 用短版，不为填模板增加前期工作。

- 按实际结果更新 README、路线图和版本记录。修改已有文件时，说明追加、局部替换或完整替换，检查 diff，避免覆盖其他内容；不要求把所有内部工作笔记公开发布。
- 有发布安排时提供与当前代码一致的 Release 标题和说明草稿，包括主要变化、验证与限制。发布前再次核对目标分支或提交；若代码或文档随后变化，更新草稿中受影响的结论。仅本地 Demo 演示时无需准备 Release、标签、发布来源或完整发布文档，但必须记录实际验收基线，不以未发布为演示验收阻碍。
- Demo 优先使用模板中的简短记录，引用已有日志与设计入口，局部更新相关路线图和说明；不重复抄写执行历史，也不为收尾另建完整文档包。每次修改工程文件后，报告实际结果、建议提交信息与是否已提交，并说明下一小目标及验收条件；已有授权与未变部分的确认继续沿用。
- 给出下一阶段交接摘要：当前分支与工作区、已验证能力、未验证和顺延项、下一步目标及验收方式。阶段结束或准备跨会话、跨 AI 接续时，可按仓库的 `templates/HANDOFF.md` 在具体项目中建立或更新交接文档，记录失败尝试及放弃原因；已有文档应局部更新当前状态，避免累积过期结论。
- 必要时提供可粘贴到新对话的简短提示词，指向交接文档及项目说明；提醒接手者重新核查 Git、代码与实际运行结果，不能把交接记录当作实现证据。
- 单独安装本 Skill、无法取得上述模板时，沿用项目已有交接格式，至少记录目标与当前一步、仓库核对入口、已完成及验证证据、阻碍和已知问题、无效尝试及原因、下一步与验收、协作约定。仅在使用者的项目中填写实际状态。
- 提交、推送、合并、打标签和发布按用户授权与仓库约定进行；整理草稿不等于执行这些操作。

## 边界

- 单个功能的开发和局部验证由实施环节负责；本 Skill 汇总版本级证据并补足必要的回归。
- 测试深度按风险决定。低影响变更不因“版本收尾”而强制生成大量重复测试；持久化、删除和不可逆操作需要与其风险相称的验证。
