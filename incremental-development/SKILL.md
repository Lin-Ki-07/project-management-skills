# 小步开发与验收

帮助个人开发者把已确认的当前目标落实为范围清楚、结果可核查的一次改动。默认用中文；遵循项目已有的协作方式、编码约定和授权边界。

## 接手当前一步

- 先确认当前小目标及验收结果；检查适用的项目说明、待改位置的周边代码、调用方、相关测试和 Git 状态。优先沿用仓库现有的命名、错误处理与模块边界；若现有写法互相冲突，说明选择及依据，不在同一处混搭风格。路线图与交接记录提供线索，实际行为以代码和运行结果为准。
- 区分用户已授权的工作、待讨论的方案和后续步骤。发现依赖或范围变化时说明影响，避免顺手扩成新功能或大规模重构。
- 开始修改前，简要说明要解决的问题、原理、具体文件与修改范围（追加、局部替换或完整替换），以及准备如何验证。用户要求先审核方案时，待其确认再改；已授权的实施工作无需重复请求许可。

## 实施与核对

1. 一次完成当前一个可验收的小目标。保留不相关的用户改动；修改已有文件后检查 diff，确认没有覆盖原内容或夹带无关变化。
2. 按风险选择验证：先运行与改动直接相关的离线检查；涉及页面交互、持久化或外部集成时，补充能观察实际行为的验证。不要把构建通过当作浏览器验收，也不要把模拟结果当作真实服务结果。
3. 报告预期与实际结果，区分“代码已写”“离线通过”“真实交互通过”“待验证”“失败”。失败时先定位触发路径和原因，再做最小修正；未通过的步骤不标完成。
4. 收尾时检查本轮是否留下调试打印、一次性脚本、临时模拟数据、写死的占位内容或无用开关。只清理能确认属于本轮且已无用途的残留；正式回归测试、测试夹具和有意保留的诊断材料不算残留。拿不准的文件说明位置与用途，保留给用户判断。
5. 功能、接口、数据结构、交互或模块职责变化时，同步检查 README、接口文档和当前执行说明是否过期。需要更新就改成当前真实规则；历史过程留给版本记录。无需更新时简要说明原因，避免让旧文档误导下一位开发者。
6. 验收通过后，给出与改动匹配的提交建议和下一步交接：改了什么、为何这样改、运行了哪些验证、剩余限制。提交、推送、合并、打标签和发布按用户授权及项目约定执行，不由本 Skill 自动触发。

## 个人开发者协作

- 用户希望亲手修改时，解释输入、输出和调用关系，给出准确位置、完整的必要代码与验证方法，再审查其改动。用户授权 AI 直接修改时，直接完成当前范围。
- UI 改动对照已确认的原型和组件状态；避免不必要的辅助标签与说明，让布局本身发挥解释作用，同时保留错误、风险和无障碍所需文字。
- 测试覆盖真实风险即可；低影响、可逆的小改动不必为了数量写重复实现的测试。真实模型、付费服务或生产数据的调用遵循用户的明确安排。

## 边界

- 版本划分和优先顺序属于路线图环节；本 Skill 只接手一个已选定的小目标。
- 设计图、计划、代码、测试各是不同证据；只有满足本步验收条件，才记录为完成。
