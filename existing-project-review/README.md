# 已有项目体检：范围与证据标准

适用于个人开发者接手自己或 AI 协作生成的现有项目，先找出影响继续开发的真实问题，再安排小步修复。此文档是体检方法，不代表任何具体项目已通过检查。

## 检查顺序

1. **确定基线**：读取适用的项目说明、当前目标、目录结构、依赖、测试入口与 Git 状态；先确认用户最关心的核心流程。计划与 README 是线索，不单独证明实现。
2. **跑核心链路**：按实际入口执行最小可行操作，记录输入、预期、实际和复现步骤。外部服务或真实数据需要用户授权时，先用离线检查并标明未覆盖处。
3. **查影响问题**：围绕已观察到的失败和近期改动，检查数据读写、错误处理、权限与参数校验、关键状态、模块边界、重复或无用代码、测试缺口和当前文档。必要时检查界面是否被无用辅助文案挤满；以可用性和任务完成情况判断，不以“像 AI 写的”作为缺陷证据。
4. **排修复顺序**：先处理数据丢失、安全或核心流程失败，再处理高频错误和维护障碍，最后处理视觉与风格问题。每项建议给出最小可验证改动；架构调整要说明实际耦合或变更成本的证据，不默认大规模重构。

## 证据与结论

每条发现记录：位置、触发条件、预期、实际、证据来源、影响、置信程度、建议的下一小步及验收方式。证据按强度区分：实际复现或测试失败、代码路径与数据结构核对、文档或报告线索。只有线索时标为“待验证”；无法运行时写明原因和最小补验方法。

特别注意 AI 协作项目可能出现的过度解释性界面、无用抽象、重复代码、未接入的功能、被覆盖的原逻辑或静默吞错。这些只是排查线索，不能仅凭命名、注释风格或文件数量断言有问题。先对照用户场景和实际行为，再决定是否修。

输出一份短清单，按优先级列出“已证实问题／待验证风险／可选优化”。对每项说明为什么现在处理或暂缓。未经用户选择，不把体检自动扩展成全面重构，也不直接删除用途不明的文件。
