# 小步开发与验收

帮助个人开发者把已确认的当前目标落实为范围清楚、结果可核查的一次改动。默认用中文；遵循项目已有的协作方式、编码约定和授权边界。

## 接手当前一步

- 新项目或新增功能在编写产品功能代码前，核对覆盖当前目标且经用户确认的 PRD，引用文档位置或对话版本及确认依据。缺失或未确认时，先回到需求收敛与 PRD 确认，可继续调研和技术可行性核实，不以路线图、小目标或助手建议替代 PRD。已有确认记录时不重复询问。
- 已有项目的小修复、文案或间距调整，可依据明确的目标和验收要求直接处理，无需补完整 PRD。发现变更影响范围、核心流程或业务规则时，先更新相关 PRD 并由用户确认，再继续受影响的实施。
- 先确认当前小目标及验收结果；检查适用的项目说明、待改位置的周边代码、调用方、相关测试和 Git 状态。优先沿用仓库现有的命名、错误处理与模块边界；若现有写法互相冲突，说明选择及依据，不在同一处混搭风格。路线图与交接记录提供线索，实际行为以代码和运行结果为准。
- 开始改代码前核对当前分支、工作区改动与项目约定的目标分支。若位置或起点不符，先说明对本步改动和验收的影响，再按用户已有安排继续或调整；不要因检查而自行切换、创建或合并分支。
- 区分用户已授权的工作、待讨论的方案和后续步骤。发现依赖或范围变化时说明影响，避免顺手扩成新功能或大规模重构。
- 开始修改前，简要说明要解决的问题、原理、具体文件与修改范围（追加、局部替换或完整替换），以及准备如何验证。用户要求先审核方案时，待其确认再改；已授权的实施工作无需重复请求许可。

## 开工提醒与简要计划

- 正式写代码前主动向用户展示一次简短的 Git 提醒：当前分支与 HEAD、工作区是否有改动及已知归属、本步建议沿用还是新建分支及理由。不能只在后台检查而不告知；同一步内无状态变化时不重复提醒。
- 沿用项目已有分支约定；没有约定时，新功能或需要独立验证的工作建议从已核实的基线创建 `codex/<主题>`，小而连续的修复可沿用当前工作分支。建议说明起点、用途及验收后如何合回目标分支；不猜测基线名，不为隔离本步而覆盖、暂存或提交用户的其他改动。
- 不在 Git 仓库中时如实提示，给出初始化版本管理的建议；不谎报分支状态，也不自行初始化。分支操作和提交按用户已有授权执行；仅给建议不等于获得操作授权，已授权时无需重复确认。
- 接着给出几条简要计划：本步目标、按顺序的改动范围、验证方法、工作日志位置。已有路线图时引用阶段和小目标编号，不另写整版计划；完成这项提示后按现有授权继续，不增加固定的开工审批。

## 实施与核对

1. 一次完成当前一个可验收的小目标。保留不相关的用户改动；修改已有文件后检查 diff，确认没有覆盖原内容或夹带无关变化。
2. 按风险选择验证：先运行与改动直接相关的离线检查；涉及页面交互、持久化或外部集成时，补充能观察实际行为的验证。不要把构建通过当作浏览器验收，也不要把模拟结果当作真实服务结果。
3. 报告预期与实际结果，区分“代码已写”“离线通过”“真实交互通过”“待验证”“失败”。失败时先定位触发路径和原因，再做最小修正；未通过的步骤不标完成。
4. 收尾时检查本轮是否留下调试打印、一次性脚本、临时模拟数据、写死的占位内容或无用开关。只清理能确认属于本轮且已无用途的残留；正式回归测试、测试夹具和有意保留的诊断材料不算残留。拿不准的文件说明位置与用途，保留给用户判断。
5. 功能、接口、数据结构、交互或模块职责变化时，同步检查 README、接口文档和当前执行说明是否过期。需要更新就改成当前真实规则；历史过程留给版本记录。无需更新时简要说明原因，避免让旧文档误导下一位开发者。
6. 验收通过后，给出与改动匹配的提交建议和下一步交接：改了什么、为何这样改、运行了哪些验证、剩余限制。提交、推送、合并、打标签和发布按用户授权及项目约定执行，不由本 Skill 自动触发。

## 持续记录工作日志

- 写代码期间，每个可验收的小步骤都写入项目工作日志；完成、失败、受阻或中途交接时及时记录，不等整个阶段结束才补写。步骤内影响后续排查的方案调整、失败尝试和修正也要记录，可合并在同一条目，不逐次记录工具调用或每次敲键盘。
- 沿用项目已有日志；没有时默认使用 `docs/WORKLOG.md`，首次开始实施时说明路径。先读取再追加，保留历史记录；更正旧结论时注明更正及原因，不静默删除失败记录。收尾检查日志 diff 并向用户提供文件链接。
- 每条记录包含：实际日期时间及所用时区、阶段与步骤编号（无编号时用简短标题）、目标和原因、分支及实施前 HEAD、修改文件及主要行为变化、验证命令或操作与实际结果、失败或未决事项、下一步。仅在实际完成提交后补记提交哈希，否则明确未提交，不将日志自身的提交要求变成循环。
- 记录足以定位问题的复现条件、错误摘要和证据位置，不粘贴完整终端流水，不写入密钥、令牌、个人敏感数据或 `.env` 内容。尚未执行的检查标为未执行；日志中的完成判断仍须有实际验证依据。
- 阶段结束时追加阶段小结，关联本阶段步骤、验收结果、已知限制与下一阶段入口；与路线图同步状态，交接文档引用日志位置而不复制全部历史。小改动可只写一个简短步骤条目，不要求另建阶段文档。

## 个人开发者协作

- 用户希望亲手修改时，解释输入、输出和调用关系，给出准确位置、完整的必要代码与验证方法，再审查其改动。用户授权 AI 直接修改时，直接完成当前范围。
- UI 改动对照已确认的原型和组件状态；避免不必要的辅助标签与说明，让布局本身发挥解释作用，同时保留错误、风险和无障碍所需文字。
- 测试覆盖真实风险即可；低影响、可逆的小改动不必为了数量写重复实现的测试。真实模型、付费服务或生产数据的调用遵循用户的明确安排。

## 边界

- 版本划分和优先顺序属于路线图环节；本 Skill 只接手一个已选定的小目标。
- 设计图、计划、代码、测试各是不同证据；只有满足本步验收条件，才记录为完成。
