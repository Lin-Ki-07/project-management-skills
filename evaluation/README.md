# 提示词与 Skill 的轻量评测

本目录提供一次改动是否值得保留的记录方法。提示词评测关注某个任务的输出；Skill 评测还要看它是否在适用场景被正确使用、是否改善了整个工作过程。先比较实际任务结果，不靠措辞印象或单一模型评分决定质量。

## 准备案例

1. 从真实请求选 3～5 个案例，覆盖常见任务和至少一个易失败场景。写清输入、必要上下文、可观察的验收项及不能发生的错误。隐去密钥、个人资料和私有路径。
2. 将至少一个案例留作最终验收；修改方案时不查看其结果来调优。案例和标准在运行前确定，避免看完输出再改评分规则。
3. 只记录与任务相关的指标：完成度、事实或代码错误、越权或遗漏、无用说明、工具调用、Token 与耗时。无法获取的成本写“未记录”，不估算成精确数值。

## 比较与决定

1. 固定同一输入、可用工具、模型和上下文边界，分别运行旧版与新版；评测 Skill 时，必要时增加不使用 Skill 的基线。环境无法完全一致时记录差异。
2. 先检查可机械验证的结果，再对主观质量做成对比较；若用模型辅助评审，隐藏版本名称并由人复核关键结论。不要把绝对分数当作唯一依据。
3. 对每个案例填写 [案例记录模板](CASE.md)，区分实际运行、离线检查和未验证。高风险错误优先于平均分；平局时优先保留更简单、成本更低的版本。
4. 每轮只改一个明确假设。留出案例通过且没有明显回归时，记录“保留”；否则记录“回退”或“继续调查”及原因。不要自动改写或发布 Skill。

少量案例只能证明覆盖范围内的效果，不能保证对所有任务都更好。完整自动化评测成本较高；个人项目先用这套记录试跑，再决定是否增加脚本或独立 Skill。
